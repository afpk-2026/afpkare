# 부모가 없는 날 재무설계 시뮬레이터 기능정의서

> 상태: 개발 착수용 초안 · 2026-11-09
> 근거: 팀의 v1.5 내용최종 검토용 PDF(2026-11-09)와 지금까지 합의한 웹 시뮬레이터 방향
> 문서의 계산값과 기관·상품 조건은 검증 상태를 함께 표시한다.

## 1. 제품 목적

성인 발달장애 자녀를 둔 가족의 **부모 노후와 자녀의 사후 생활비를 한 예산 안에서** 비교한다. 가정을 바꾸면 두 세대의 자금 경로와 공적급여가 어떻게 달라지는지 계산하고, 결과에 사용한 보고서 표·식과 미확인 전제를 보여 준다. 첫 배포는 공모전 시연용 가상 사례 웹앱이다. 실제 수급·세액·상품 가입을 확정 판정하지 않는다.

### 성공 기준

1. 기준 사례를 열고 가정 하나를 바꿔 변경 전·후 결과를 비교할 수 있다.
2. 기본 가정에서 보고서의 83세 필요 잔액 **1.30억 원**, 95세 필요 잔액 **1.75억 원**, B안의 56세 예상 잔액 **1.81억 원**을 대조한다. 수치 일치만으로 산식의 정확성이 증명되지는 않으므로 계산 순서와 경계값도 확인한다.
3. 결과마다 사용한 입력, 기준 연도, 계산/미확인 상태, 보고서 연결 위치가 표시된다.
4. 구현하지 않은 사건이나 상품 조건을 계산된 결과처럼 표시하지 않는다.
5. 공개 URL에서 열기 → 변경 → 비교 → 초기화 흐름이 동작한다.

## 2. 사용자와 핵심 흐름

- 첫 사용자: 공모전 심사위원과 팀원. 가상 고객의 결론이 어떤 가정에 의존하는지 살펴본다.
- 실제 가족·재무설계사의 상담 사용은 첫 배포 범위가 아니다.

`지훈 씨 가족 선택 → 전략과 가정 확인 → 입력 또는 사건 변경 → 두 세대 그래프·대안 비교 → 결과 근거 확인 → 초기화`

| 우선순위 | 기능 | 첫 배포 범위 |
| --- | --- | --- |
| P0 | 기준 사례 | 지훈 씨 가족 한 사례, 2026년 가격·제도 기준, 가상 데이터 배지 |
| P0 | 직접 변경 | 부모 사후 월 생활비, 자녀 유족연금, 신탁 순실질수익률, 부모 재취업 월소득, 자녀 설계 종료 나이 |

| 제외 | 계정·서버 저장·실고객 데이터·상품 추천/가입·자유로운 법률 해석 | 첫 배포에서 구현하지 않음 |

| 카드 | 바뀌는 값 | 핵심 비교 |
| --- | --- | --- |
| 부모 노후 압박 | 재취업 월소득 200만 → 0원 | 부모 금융자산 고갈 |
| 유족연금 불확실 | 자녀 유족연금 107만 → 0원 | 필요 신탁액 증가 |
| 생활비 증가 | 사후 생활비 180만 → 220만 원 | 자녀 부족액·전략 유지 가능성 |

## 5. 기능 요구사항

### F01 기준 사례와 초기화 [P0]

- 첫 화면은 **95세 목표 1.75억 원**과 **B안의 예상 56세 잔액 1.81억 원**을 구별한다. 1.30억 원은 83세까지의 비교값이다.
- 초기화하면 입력, 전략, 사건, 비교 결과가 기준 사례로 돌아간다.
- 가상 사례와 계산 규칙의 버전을 표시한다.

### F02 입력 변경 [P0]

- API 금액은 원 단위 정수, 화면은 만원·억원으로 변환한다. 나이와 비율은 단위를 분리한다.
- 지원 필드: `monthly_child_cost`, `monthly_survivor_pension`, `net_real_return`, `monthly_parent_reemployment_income`, `child_end_age`.
- 변경안 미리보기와 `적용` 버튼을 둔다. 금액의 음수·형식 오류·허용 범위 밖 값은 거부한다. **수익률은 음수도 허용할 수 있으므로** 필드별 범위를 따로 확정한다.
- 실명·연락처·건강정보 입력 필드는 제공하지 않는다.

### F03 전략 선택 [P0]

| 전략 | 보고서상 정의 | 화면 상태 |
| --- | --- | --- |
| A | 지금 1.3억 원 + 사후 재산의 3/4 이전 | 과다 이전 비교 |
| B | 원금 1.30억 원 자익형 단계 적립 | 설계상 기준안. 실상품 실행 조건 미확인 |
| B′ | 원금 1.00억 원 + 사후 보충 0.35억 원 | 보충 재원·상품 조건 미확인 |
| D | 별도 준비 없이 법정상속 | 기준 비교 |
| E | 누나에게 금전 부담 | 가족의 ‘누나 금전 기여 0원’ 제약 위반, 참고만 |

- 표 8의 `56세 잔액 5억 원`은 민감도 사례이지 A안이 아니다.
- 보고서 **표 9**의 A/D 비용·후회는 기준 사례의 고정 비교로만 표시한다. 입력을 바꾸면 A/D의 동적 결과는 `계산 미지원`으로 둔다. **P0 완료의 필수 범위는 B/B′의 입력 변경 재계산과 부모·자녀 경로 두 개**다. B/B′의 필수 지표가 미완성이면 P0 미완료로 판정한다.
- 자동 권고보다는 비교 결과, 가족의 제약, 미확인 실행 조건을 보여 준다.

### F04 계산 결과와 그래프 [P0]

- 자녀: 연도/나이별 신탁 잔액, 인출액, 급여, 생활비 부족액. 지훈 씨 65세의 연금 규칙은 **자동 전환**한다.
- 부모: 연도별 금융자산, 최저값, 첫 음수 연도. 계획 가능성은 `부모 금융자산 최저값 ≥ 0`으로 판단한다.
- 부모 금융자산과 자녀 신탁 잔액은 그래프를 분리한다. 정년·국민연금 개시·부모 사망·자녀 65세를 표시한다.
- 순실질수익률은 이미 보수 차감 후의 값이므로 미확인 상품 보수를 임의로 다시 빼지 않는다.
- 공적급여 계산에 지훈 씨 명의 예금 1천만 원을 누락하지 않는다. 예금 유지/사용 가정을 근거 패널에 적는다.
- 부족액·급여 손실·최대 후회는 같은 사건·기간·가격 기준에서만 비교한다. 변경 입력의 최대 후회는 첫 배포 계산 범위가 아니며, 기준 사례 고정값과 혼합하지 않는다.

### F05 근거와 한계 [P0]

각 결과에서 입력값, 적용 규칙, 보고서 표·식 번호, 2026년 가격·제도 기준, 계산 상태를 볼 수 있어야 한다. 계산 상태는 `직접 계산`, `보고서 고정값`, `미구현`, `해석 미확인`으로 구별한다. 자익형 납입 조건, 신탁 보수, 유족연금 생계유지 인정, 그룹홈 주거급여 등은 확인 과제로 표시한다.

### F06 샘플 사건 [P1]

| 버튼 또는 표시 | 처리 |
| --- | --- |
| 재취업 실패·월 100만 원 | 재취업 입력 변경 후 부모 최저 금융자산 재계산 |
| 생활비 월 185만 원 | 사후 생활비 변경 후 필요액·전략 비교 |
| 95세 생존 | 기본 목표. 83세와 비교하는 설정으로 제공 |
| 지훈 씨 65세 | 버튼 없음. 타임라인의 자동 전환점 |
| 신탁 잔액 5억 원 | 표 8 민감도 비교, A안과 분리 |
| 어머니 선사망·25세 부모 사고 | 유족연금 귀속·돌봄비·보험금·상속을 함께 검증하기 전에는 정적 설명 카드 또는 비활성 |

### F07 자연어 변경 제안 [P1]

`“생활비가 월 185만 원이면?”`을 지원 필드의 변경안으로 변환한다. LLM은 금액 결과나 법률 판정을 만들지 않는다. 사용자 확인 뒤에만 계산 API를 호출한다. 모호한 입력은 자동 적용하지 않는다. 외부 호출 실패나 API 키 부재 시 수동 입력은 작동한다. 개인정보 제거와 입력 검증이 불충분하면 첫 배포에서는 자연어 기능을 비활성화한다.

## 6. 계산 계약과 검증

1. **단일 계산원:** FastAPI의 Python 함수가 계산한다. 프론트엔드는 표시·서식만 담당한다.
2. **단위·시간:** 금액은 원 단위 정수로 다룬다. 납입·인출·수익 반영 순서를 명세와 시험에 고정한다. 연도/나이와 2026년 실질 가격을 명시한다.
3. **모듈 경계:** 공적급여, 자녀 신탁 현금흐름, 부모 금융자산, 대안 비용 계산을 분리한다. 연도별 제도 기준값도 별도 데이터로 둔다.
4. **재현 대상:** 1.30억·1.75억·1.81억, 표 8 주요 행, 그림 6 경로, 표 9 비교값을 대조한다. 차이가 있으면 반올림·연령 전환·명의별 재산 포함 범위와 계산 순서를 확인해 기록한다.
5. **경계값:** 64→65세, 급여 감액·중단점, 신탁 0원, 유족연금 0원, 재취업 0원, 수익률 0%, 생활비 185만 원, 83→95세.
6. **변화 방향:** 생활비 증가가 필요 잔액을 감소시키지 않는지, 재취업 소득 감소가 부모 자산을 증가시키지 않는지 확인한다. 제도 비선형 구간에서 예외가 나오면 산식과 조건을 조사한다.
7. **점검 지표:** 보고서 표 11의 `신탁 잔액 ÷ 1.19억`을 그대로 수급 자격 판정으로 옮기지 않는다. 자녀 총재산·소득을 반영해 다시 정한다. 3.35억 원의 감액 시작과 4.40억 원의 중단도 구별한다.

## 7. 화면 구성

데스크톱 단일 페이지를 우선한다. 상단에 목적·가상 사례 배지·계산 상태, 왼쪽에 기준 사례·전략·입력·샘플 사건, 중앙에 목표/예상 잔액과 부모·자녀 그래프, 오른쪽에 보고서 산식·미확인 전제, 아래에 대안 비교를 둔다. 좁은 화면은 `설정 → 결과 → 근거 → 비교` 순서로 쌓는다. 그래프 핵심값은 텍스트·표에도 표시하고, 색만으로 위험·미확인을 구별하지 않는다.

## 8. 기술·배포 구조 제안

| 층 | 초안 선택 | 이유 |
| --- | --- | --- |
| 프론트엔드 | **Vite + React + TypeScript** | 입력·그래프 중심 단일 페이지. 정적 빌드로 별도 프론트 서버 불필요 |
| 백엔드 | **FastAPI + Python** | 계산·입력 검증·JSON 응답을 한곳에서 관리 |
| 데이터 | 버전 관리되는 가상 사례 설정 파일 | 저장 없는 공개 데모로 확정. DB·계정 없음. 새로고침하면 초기화 |
| 선택적 LLM | FastAPI에서만 호출 | P1. 키는 서버 환경 변수 |
| 앱 배포 | Vultr 단일 인스턴스의 Docker Compose | 정적 프론트·API·리버스 프록시를 한 서버에 배치 |
| 인프라 | Terraform `infra/` | 인스턴스·SSH 키·방화벽 등 생성. 앱 배포·비밀값 주입은 별도 |

프론트 `/`와 API `/api/`를 같은 출처에서 제공한다. **도메인 없이도 Vultr 인스턴스의 공인 IP로 개발·배포할 수 있다.** 초기 시연 주소는 `http://<공인 IP>/`로 두되, HTTP에서는 실사용자 정보·인증·민감정보 입력을 허용하지 않는다. 제출용 URL은 공인 IP 주소의 지속성·접속 가능성을 확인하고, HTTPS가 필요하면 도메인 또는 별도 인증서 경로를 추후 정한다. Vultr API 키·LLM 키·Terraform state·`.env`는 저장소에 올리지 않는다. Terraform 적용은 서버 생성이고 앱 버전 배포·롤백은 별도 절차다.

**API 초안:** `GET /api/health`, `GET /api/reference-case`, `POST /api/simulations`, 선택적 `POST /api/parse-change`. 구현 전 입력·응답 스키마를 한 번 더 확정한다.

## 9. 비기능 요구사항

- 공개 데모에서는 가상 가족 값만 받는다. 실명·연락처·건강정보를 수집·저장하지 않는다.
- API는 입력 형식·크기·허용 범위를 검증한다. LLM 키는 브라우저로 전달하지 않는다.
- 계산 오류를 그럴듯한 숫자로 대체하지 않는다. 오류 상태와 다시 시도 방법을 보여 준다.
- 화면에는 `가상 사례 비교이며 수급·세금·상품 계약의 확정 판정이 아님`을 짧게 표시한다.
- 배포 전 실제 브라우저에서 기준 사례 열기 → 변경 → 비교 → 초기화 전체 흐름을 검증한다.
- 배포 버전, Terraform plan, 서버 접근·롤백 방법을 기록한다. 서버 저장을 도입하면 백업·복원 설계가 선행돼야 한다.

### 13.1 PDF에 명시된 식과 구현 전 확인할 순서

다음은 **보고서의 수학적 구조를 옮긴 것**이다. 구현 코드의 확정 알고리즘은 아니다.

- 자녀 신탁(식 1): `F[t+1] = (F[t] - 12 × w[t]) × (1 + r)`, `w[t] = min(max(0, N - Y[t] - B(F[t])), 월 인출 한도, F[t]/12)`.
- 최소 필요 잔액(식 2): 56세 시작 잔액 후보를 바꾸며 대상 기간의 모든 해에서 `N - Y[t] - B(F[t]) - w[t] ≤ 0`을 만족하는 가장 작은 금액을 찾는다.
- 부모 금융자산(식 3): `W[y+1] = W[y] × (1 + r) + L[y] + R[y] + P[y] + H[y] - C[y] - X[y] - M[y] - I[y] - K[y]`. 보고서의 `r`이 부모 금융자산에도 동일한 순실질수익률인지 명시되지 않았다.
- 비용·후회(식 4): `cost(a,s) = 3 × lifetime_shortfall(a,s) + lost_benefits(a,s)`; `regret(a,s) = cost(a,s) - min(cost(eligible_alternative,s))`; 전략별 최대 후회는 네 사건의 최대값. 반올림 전 값으로 계산한다.

보고서의 식 1은 연간 잔액을 사용하면서 `w`는 월액으로 정의한다. 따라서 월급여를 어느 시점의 잔액으로 평가하는지, 월 인출을 연초에 12개월분 한 번에 차감하는지, 인출 직후 잔액의 음수 방지 순서, 95세 해를 포함하는지 등은 **팀 확정 전까지 구현 기준으로 단정하지 않는다.** 식 3도 연간 현금흐름의 발생 시점과 퇴직소득세 반영 경로가 결정돼야 그림 6을 재현할 수 있다.

## 14. 첫 배포의 계산 완료 범위와 API 계약 초안

### 14.1 P0의 완료 조건

1. 기준 사례와 사용자가 변경한 사례에 대해 **B와 B′의 자녀 신탁 연도별 경로** 및 **부모 금융자산 연도별 경로**를 계산한다.
2. B/B′ 각각의 56세 예상 잔액, 95세까지의 생활비 부족액·부족한 해, 부모 금융자산 최저값·첫 음수 연도를 반환한다.
3. 83세·95세 최소 필요 잔액과 65세 급여 전환을 계산한다. 기준 사례와 변경안 모두 같은 계산 함수를 사용한다.
4. A/D는 **입력을 바꾸지 않은 기준 사례**에서만 표 9의 고정 비용·후회와 `보고서 고정값` 배지를 보여 준다. 입력이 바뀌면 A/D 결과는 비활성·`동적 계산 미지원`으로 표시한다.
5. B/B′의 네 사건별 비용·최대 후회는 사망·상속의 완전한 동적 계산이 없으면 **P0 필수 지표가 아니다.** 기준 사례의 표 9 비교는 고정값 배지로만 보여 주고, 변경 입력에 따른 `새 권고`를 자동 산출하지 않는다.
6. 1~3을 구현·검증하지 못하면 P0 완료로 표시하지 않는다. 화면 골격과 고정값 표시는 별도 진척으로 기록한다.

### 14.2 임시 API 스키마 제안

기존 코드는 없으므로 아래는 **구현 전 팀 확정 대상인 제안**이다. 지원하지 않는 필드는 서버에서 거부하며, 프론트엔드도 같은 필드 목록을 사용한다.

| 요청·응답 | 필드 | 의미 |
| --- | --- | --- |
| `GET /api/reference-case` | `case_id`, `source_version`, `base_year`, `defaults`, `evidence` | 가상 기준 사례·보고서 버전·입력 상태 |
| `POST /api/simulations` 요청 | `case_id`, `strategy` (`B`/`B_PRIME`), `overrides` | 변경 입력. A/D의 동적 요청은 지원하지 않음 |
| 성공 응답 | `calculation_status`, `effective_inputs`, `child_timeline`, `parent_timeline`, `summary`, `warnings`, `source_refs` | 숫자와 계산 근거를 함께 반환 |
| 계산 미지원 | `status: unsupported`, `reason`, `unsupported_fields` | 200 성공 결과와 구별. HTTP 코드와 상세 형식은 구현 전 확정 |
| 입력 오류 | `status: invalid_input`, `field_errors` | 필드별 단위·범위 오류 |

`summary`에는 `required_trust_at_56`, `projected_trust_at_56`, `child_shortfall_total`, `child_shortfall_years`, `parent_asset_min`, `parent_first_negative_year`를 포함한다. 연도별 배열은 `year`, `child_age` 또는 `parent_age`, `start_balance`, `inflows`, `outflows`, `benefits`, `end_balance`처럼 실제 산식에 대응하는 이름을 쓴다. 모든 금액은 원 단위 정수로 직렬화하고, 표시 단위만 프론트에서 바꾼다.

### 14.3 입력 검증 원칙

- 금액 입력은 0 이상이다. 0원은 유족연금·재취업 소득에서 유효한 시나리오다.
- **순실질수익률은 음수도 경제적으로 가능한 입력**이므로 일괄 음수 거부 대상이 아니다. 수학적으로 `r > -1`을 요구하며 제품 허용 범위와 소수 정밀도는 팀이 정한다.
- 종료 나이는 부모 사망 시 지훈 씨의 나이 56세보다 작을 수 없다. 상한·포함 연도는 팀 확정이 필요하다.
- 서버는 NaN·무한대·잘못된 단위·지원하지 않는 필드·과도한 요청 크기를 거부한다. 임의로 값을 잘라 적용하지 않는다.
